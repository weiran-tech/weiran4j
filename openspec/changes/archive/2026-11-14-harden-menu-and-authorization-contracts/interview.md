## 边界

### 要做

- 菜单结构变更在数据库内串行化，普通编辑加入版本冲突保护。
- 服务端跨实例授权快照按共享修订号校准；前端统一读取身份及菜单快照，有界刷新、前台恢复校准、403 恢复且不重放写请求。
- OpenAPI 反映真实成功包络及错误 schema，覆盖既有包络、字符串、列表、分页和跳过包装的边界。
- 同步 docs 的菜单冲突、授权变化/失败重试演示，更新现状文档。

### 明确不做

- 短信/MFA/手机号绑定挑战共享存储。
- 日志查询优化、依赖分层专项治理、分支保护设置。
- 全平台请求幂等、其他资源全面版本化、引入 Redis 或消息总线。
- 全量生成并替换前端 API 客户端。

### 本次不决定(留给后续 change)

- 大规模授权数据的增量推送、按角色细分修订号及性能专项优化；先采用适合后台底座的共享全局修订号。

## 验收标准

- [ ] AC-1 两个独立事务并发互挂菜单时，最多一个成功，最终无环；父节点删除与子节点新增竞争不产生孤儿。
- [ ] AC-2 菜单旧草稿写入返回 409/100007，保留草稿，用户确认重载后才替换编辑基线。
- [ ] AC-3 A 实例提交授权变更后，B 实例此后开始的鉴权不得沿用旧修订号的权限快照；事务回滚不发布修订号。
- [ ] AC-4 可见且在线页面每 30 秒发起授权校准，回前台和重连立即校准；身份与菜单以同一快照一起替换。
- [ ] AC-5 403 发起去重校准但不自动重放原写请求；刷新失败保留上次快照并展示持续失败及手动重试入口；401 仍清会话。
- [ ] AC-6 /v3/api-docs 的成功响应 schema 与真实包络一致，已包络不重复包装，非包装响应保留原 schema，失败按真实 ErrorResponse 描述。
- [ ] AC-7 真实 HTTP、并发事务和前端定时/可见性/失败恢复回归通过，docs 以实际交互逻辑及本地数据覆盖新增状态。

## 关键取舍

| 取舍点 | 选择 | 放弃的方案 | 理由 |
|---|---|---|---|
| 菜单层级一致性 | 数据库结构守卫 + 单行编辑版本 | 仅单行版本或进程锁 | 跨行环路和跨实例竞争需要共享串行化边界 |
| 授权一致性 | MySQL 共享修订号 + 原有本地缓存 | Redis 广播、每次全量查权限 | 复用已有存储，保持缓存收益并消除跨实例 TTL 窗口 |
| 前端校准 | 一个身份/菜单快照 + 有界刷新 | 分开两次查询分别替换 | 避免导航与按钮短暂来自不同授权版本 |
| OpenAPI | 自动从运行时包装策略生成 schema | 手写逐接口响应复制 | 减少接口增长后的契约漂移 |
