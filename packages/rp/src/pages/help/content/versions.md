# 版本管理与历史

版本清单位于独立的[版本管理页](/versions)，首页提供入口，点击版本进入公共版本详情；说明编辑、评审与验收沿用首页导航，无需登录演示管理端。顶部可切换版本或返回清单；打开具体原型后才进入管理端或手机端。

## 原型、改动和评审在同一页

版本详情 `/versions/<版本>/rp/versions` 的“原型与改动”直接展示页面目录，通过目录筛选行右侧的“完整产品 / 本版改动”按钮组切换查看范围，通过标题下方“全部 / 管理端 / 手机端”按钮组筛选页面，目录按模块纵向列表展示；右侧完整双端原型按钮始终保留，直接打开完整产品，不受目录筛选影响。“改动说明”按钮在当前页打开抽屉。版本记录与评审沿用同一版本上下文；维护摘要与指南直接展示；页面不再提供研发与验收分区、交接编辑或归档操作。

旧 `/versions/<版本>/rp/demo` 地址跳转到版本详情，并保留范围、端、场景和改动等参数。目录不再使用独立页面；管理端和手机端原型内仍可通过“本页改动”打开说明抽屉。

站内只可创建、维护版本记录，新增版本初始没有改动。CHG 统一由 AI 编程工具随源码、菜单和 Mock 提交；旧草稿中的手工改动先备份，读取时恢复仓库说明。

## 按版本与完整产品

版本只由路径确定，例如 `/versions/v0.8/rp/versions?scope=version`。切换版本会修改路径；`scope=version` 查看本版新增、修改、删除项，`scope=all` 查看这个版本的完整产品。路径中的 v0.8 不会被旧 `version=v0.1` 参数覆盖，系统会移除冗余参数。

新版本选择已定版版本作为基线，首次版本可无基线。完整产品只沿所选基线链合并，同基线的其他版本不会自动纳入。

每版指定一个基线：完整产品 = 基线的全部有效页面、菜单及交互 + 本版新增和修改 − 本版删除。未改动页面继续保留，整个版本没有页面改动时完整产品与基线一致，不需要编造 CHG。无改动版本仍需填写目标、基线和评审记录。

`prototype/page-baselines.json` 保存从 v0.2 固定源码提取的起始页面清单，不使用最新菜单反推历史。之后按稳定的 `platform + pageId` 继承、覆盖或删除，改名及改路径保持页面编号不变。完整目录标识“本版未改动 · 沿用基线”。

新构建内的 `product-pages.json` 保存完整页面清单、基线和提交号；完整原型构建同时保留当时菜单与交互。制作中允许更新，评审读取固定候选，定稿保留完整不可变快照。页面清单缺失会明确提示；历史实际页面只从对应快照打开，不能使用当前工作构建补位。

例如 v0.8 基于 v0.2，账户管理未改动仍在完整目录中，退款交互使用 v0.8 的改动；删除项只在本版改动中保留删除前页面入口，不出现在完整目录。

## 原型查看、嵌入与历史

从目录打开单个页面或对应版本的完整原型。页面并排对比已移除；旧链接中的 `compare`、`baseline`、`view` 参数会清除，版本、范围、端和改动说明继续保留。

嵌入参数 `embed=page` 隐藏导航、侧栏、顶部、Tab 和评审工具；`embed=full` 保留完整产品。手机端使用 Vant，可独立打开或在预览框操作。单页链接保留场景与改动上下文。

旧快照不支持新参数时，仅在同域容器追加隐藏外壳的样式，不修改历史附件；跨域嵌入依赖目标页面自己支持参数。

旧阶段 development / acceptance 展示为已定稿，delivered 展示为已验收；原始字段、旧上线完成条件和历史版本不改写。历史交接只读，新工作在承接版本继续。


## 同基线同页面的并行调整冲突

版本详情“原型与改动”和“版本记录”会检查其他已登记版本：基线相同，且端与稳定页面编号相同时列出对方版本、页面及双方 CHG。版本记录表单可调整本机版本元信息；改动内容只读取仓库登记。

修改与删除、双方新增同一页面也视为冲突。不同端、不同基线、无基线及已承接版本不计入冲突。同页多项 CHG 合并成一条页面冲突，页面改名但编号不变时仍能识别。

未解决冲突会阻止继续编辑、开发和构建，评审入口保留以便协商解决。先核对并统一交互和规则，再通过 `pnpm version:work` 登记解决结论及代码或评审证据；不会自动合并，也不能判断尚未登记的其他分支源码。

## 版本 JSON 与完整产品

仓库 `prototype/releases.json` 是共享版本数据。网页“创建版本”先建立本机草稿，不提供导入、导出或下载；由维护者通过 AI 编程工具将版本信息写入仓库并提交 PR。纯前端页面不声称自动写入项目目录。也可运行 `pnpm version:new -- v0.9 "标题"` 直接创建仓库 JSON。

## 路由与版本隔离

| 分区 | 当前入口 | 版本页面示例 |
| --- | --- | --- |
| 原型协作 | `/` | `/versions/v0.8/rp/versions` |
| 管理端产品 | `/manage` | `/versions/v0.8/manage/refund-demo` |
| 手机端产品 | `/mobile/` | `/versions/v0.8/mobile/#/orders` |

`/manage` 和 `/mobile/` 是当前工作版本的快捷入口，打开后进入版本路径。根 `/` 提供入口，`/versions` 独立展示全部版本，两者均不带版本参数；点击详情进入 `/versions/<版本>/rp/versions`，真正预览从对应版本构建读取。使用指南通过首页或工作台的帮助入口进入，路径为 `/help/<文章>`。业务页面不允许用 `?version=其他版本` 冒充版本切换。

`/versions/版本号/` 是该版本持续更新的工作构建，资源前缀独立。正式评审使用 `/releases/版本号-rc-提交/`，已定稿版本使用 `/releases/版本号/`；固定构建不覆盖。旧归档仍使用其原来的业务路径，不强制迁移历史文件。不存在的版本或资源返回 404，不回退到当前代码。

Mock、退款数据、登录会话、偏好、页签和表格配置按版本或候选构建编号隔离。切换后可能需要重新登录；旧浏览器数据保留，不清空其他版本。源码仍按业务目录维护，构建时分别输出根目录入口和当前版本产物。

顶部“查看版本”使用 Semi Select 切换版本，保留原型范围和适用端。版本详情通过“原型与改动 / 评审与结论”页签切换，内容与概览卡片对齐，不叠加外层缩进。

顶部导航不再提供“进入原型”快捷入口；从版本清单点击“进入版本”按钮打开对应版本详情。

## 开始工作前先明确版本

产品给 AI 的需求应带上目标版本、固定基线和页面编号，例如：“在 v0.9（基线 v0.2）调整手机订单详情，先执行 `pnpm version:work -- v0.9`，检查通过后再修改页面、Mock 和本版 CHG。”没有目标版本时先选择版本；新版本使用 `pnpm version:new -- v0.9 "标题"` 创建仓库记录。

只有已完成评审并定稿的版本可作为基线。待评审不等于评审通过，未评审源码基线也不能直接派生新版本。

同一基线派生版本若调整同端同页，未解决前不能继续编辑、开发或构建。先统一实现与规则，再登记解决结论、对应代码或评审证据。`prototype/conflict-resolutions.json` 随源码共享，绑定双方当前页面内容；任一方内容变化后自动重新阻塞。此操作不代替评审批准。

## 双端介绍、备注与版本导出

版本详情的“版本介绍与评审备注”可编辑 PC / 手机端整体介绍，也可选择完整目录中的页面填写介绍、备注。源码的 `platformNotes`、CHG 的 `introduction` / `remark` 是共享默认内容；产品补充内容保存在本机，按版本、端和页面隔离，不自动覆盖仓库。

导出 HTML 或 JSON 会包含所选版本的完整双端目录、介绍及本机评审记录，不受目录端筛选或“本版改动”范围限制。HTML 包含评审图片，可用浏览器打印为 PDF。不同浏览器的本机备注需要分别导出，不会自动汇总。
