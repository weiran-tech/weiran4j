# 产品、评审与研发协作

日常流程：**制作中 → 评审中 → 已定稿 → 已验收**。版本详情默认进入“原型与改动”，另外提供评审分区。业务上线独立记录。

## 阅读与编辑

默认只读，阶段、负责人和研发结果来自已发布的 GitHub 共享摘要；没有摘要时明确提示待同步，以主评审记录 为准。本机未提交草稿不会显示为团队结论。

交接记录在 GitHub 维护，站内不提供交接编辑、表单、导入导出或版本归档操作。维护区只展示基线、改动数量、同步时间和维护指南。

阅读路径为“协作首页 → 版本详情 → 选择改动 / 查看原型”。点击改动后在抽屉阅读前后说明、规则和验收条件；完整页面统一在当前“原型与改动”目录查看，保留未改动页面入口。手机预览直接选页，二维码按需展开。

## 岗位职责

| 岗位 | 负责内容 | 交接产物 |
| --- | --- | --- |
| 产品 | 页面、业务规则、版本范围、评审组织及验收 | 完整原型、改动说明、验收条件和本人结论 |
| 技术负责人 | 确认可实施性、分配任务、明确暂缓范围 | 技术本人确认、每项改动的负责人和真实任务 |
| 研发 | 在业务仓库实现并提测 | PR 或无需代码原因、测试环境、业务构建 |
| 测试 | 参与规则和异常场景评审，协助验收 | 测试结果和证据 |
| 维护者 | 固定候选、在线定稿检查、摘要同步及部署 | 可访问的固定版本、来源清楚的共享记录 |

## 阶段条件

| 阶段 | 操作和下一步条件 |
| --- | --- |
| 制作中 | 产品完成页面、修改内容、规则、异常和验收条件。维护者登记主评审记录、生成固定候选；产品补齐确认人、团队 HTTPS 地址和数据初始化方式后发起评审 |
| 评审中 | 每版一个 Discussion，独立问题一个评论串；采用的意见同步回原型和说明。阻塞全部有结论且完成产品复核后，产品、技术分别对当前候选本人确认，由维护者执行定稿归档 |
| 已定稿 | 研发按固定版本逐项接单。接单填负责人和任务，提测再填实现、环境和构建。产品按原条件验收 |
| 已验收 | 全部改动已验收，或有明确暂缓 / 无需研发结论。暂缓需原因和后续任务，单独显示，不统计为已验收项。业务发布无需完成即可结束需求验收 |

评审信息在 GitHub 中补齐，站内展示同步结果。研发任务、验收及发布在团队任务系统和 GitHub 中记录，站内不提供这些操作。网页不能代替在线归档，不能通过手动选择阶段伪造定稿。

## 三个交接点

1. 产品交给评审：完整产品可操作，版本目标、改动、规则和验收条件齐全。
2. 评审交给研发：固定原型体现最终决定，问题有采用 / 暂缓 / 不采用结论；研发无需从评论中猜测需求。
3. 研发交给产品：提供准确环境和构建，产品按原条件逐条核对并本人确认。

定稿后的新增需求、规则或验收条件变更进入下一版本；实现不符登记缺陷并关联原改动编号；勘误保留记录，固定快照不覆盖。

操作细节从帮助页面按产品、评审和研发选择指南。历史流程以原候选和 Git 记录为准。
