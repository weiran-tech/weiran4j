> 本文件记录 monorepo 重做过程中的关键决策与理由，只增不改（新决策追加，旧决策标记「已取代」）。

## D-001 仓库范围（2026-09-03）

weiran4j 作为 monorepo，包含四部分：

1. **Java 后端**（Gradle 多模块）—— 核心
2. **前端 web**（pnpm，参考 mono4ts/packages/web 技术栈）
3. **openspec 工作流**（复用 mono4ts/openspec 的 L0–L10 闸门流程，适配 Java 命令）
4. **CLAUDE.md / AGENTS.md 仓级 AI 协作规范**

## D-002 底座依赖方式（2026-09-03）【已取代 → D-008】

以 **Maven 依赖 + BOM** 方式消费公司底座 [wuli3-gradle](https://github.com/Y-cs/wuli3-gradle)，
不做 git submodule、不 vendor 源码。

- 理由：仓库解耦、构建轻、底座升级只改版本号。
- 代价：底座未发布到公共仓库时需先 `./gradlew publishToMavenLocal` 本地调试。
- build-logic 约定插件无法跨仓复用，weiran4j 自建一份 `build-logic`，照搬底座的质量规则
  （JDK 21 toolchain、Checkstyle、Error Prone + NullAway、禁 `java.util.Date`、JSpecify 空安全）。

`<module>-adapter` / `-api` / `-application` / `-domain` / `-infrastructure`。

- 差异：kjs-main4j 用 Maven，weiran4j 用 Gradle（底座是 Gradle）。

## D-006 关闭 Gradle 配置缓存（2026-09-04）

Spotless 的 palantir-java-format 步骤与 Gradle 配置缓存不兼容：配置缓存恢复的类加载器
拿不到 `--add-exports` 的模块开放，palantir 在 `JavaInput.<clinit>` 抛
`IllegalAccessError`（访问 `com.sun.tools.javac.util.Log`），被 Spotless 包成
`palantir-java-format(InvocationTargetException)` 报为 lint 错误。

**定位过程**（记下来是因为症状极具误导性）：

1. 失败文件集合每次都变（实测 3 → 1 → 2），一度以为是构建缓存坏了；
   实际是已通过的文件 UP-TO-DATE 不再重跑，所以只剩「尚未成功过」的文件在报错。
2. 排除了：`clean` 与并行任务竞争、daemon 复用、构建缓存、文件内容（逐字节对比过
   通过与失败的两个同形状 `package-info.java`，完全一致）。
3. 用 palantir 的 jar 单独跑那个文件，才拿到被 Spotless 吞掉的真实异常。
4. 对照实验：`--no-configuration-cache --rerun-tasks` 连跑 3 次全绿。

**决定**：关闭配置缓存。代价是冷构建配置阶段慢几秒；收益是门禁不再随机变红。
不可信的门禁比没有门禁更糟——它会训练人忽略红灯。

已登记为 `openspec/state/waitlist.md` 的 T-001，Spotless 修复后可重新打开。

## D-008 框架重写：去 wuli3、不兼容 PHP、对标 mono4ts 后台底座（2026-09-26）

仿照 `/Users/duoli/Projects/hanrui-jinnuo/mono4ts`（Hono + Drizzle + Semi 的后台）的能力形态，
把 weiran4j 重写为 **Java 21 + MySQL 8 + Semi UI** 的后台管理框架底座。原地重写，旧实现可从 git 历史回溯。

决定（经用户确认）：

1. **能力范围 = 标准后台底座**：登录/JWT、用户、角色、菜单（动态路由 + 按钮权限）、部门、字典、系统配置、
   登录日志、操作日志；前端 AdminLayout（侧边菜单、多页签）。mono4ts 的业务台账 / 工作流 / 报表不在范围内。
2. **保留 DDD 五层**：`weiran-system`（身份与权限）与 `weiran-platform`（字典 / 配置 / 操作日志）各五层（已由 D-011 合并为 `weiran-base`）。
3. **去掉 wuli3 底座**：直接基于 Spring Boot 3.5 + MyBatis-Plus + Flyway；新增 `weiran-framework`
   承担统一响应、全局异常、认证拦截、权限注解、操作日志切面等原先由 wuli3 提供的职责。
   理由：wuli3 未发布到任何远程仓库，新 clone 无法构建（原 T-002），且其字符串 `code` 与前端生态不一致。
4. **不兼容 PHP weiran-v1**：不再读写 `pam_*` 表、删除历史密码算法与 Ban 功能、`/api/v1` 前缀改为 `/api`。
   原宪法 CP-7 / CP-8（迁移期约束）改写为 Flyway 迁移不可变 / BCrypt + token_version。

契约文档：[`01-架构与接口契约.md`](01-架构与接口契约.md)。
代价：旧的 4 份 openspec 主 spec 全部标为 `superseded`；`docs/10-模块映射.md`、`docs/20-数据迁移注意事项.md` 删除。

## D-011 合并 weiran-system 与 weiran-platform 为 weiran-base（2026-09-30）

- 两个模块合并为 `weiran-base`（后台基座），仍是 DDD 五层：`:weiran-base-{api,domain,application,infrastructure,adapter}`。
- **只合并 Gradle 模块，不改 Java 包名与 Flyway 目录**：包仍是 `com.weiran.system.*` / `com.weiran.platform.*`，
  迁移脚本仍在 `db/migration/system/` 与 `db/migration/platform/`。改目录会让 Flyway 记录的脚本路径与校验和对不上（CP-7）。
- 理由：三层划分（框架 / 基座 / 业务）里，身份权限、日志、字典配置同属"所有业务都要用的通用后台能力"，
  且二者本来互不依赖，合并不引入新的耦合；登录日志（system）与操作日志（platform）也回到同一模块。
- 代价：`system` 与 `platform` 之间不再有 Gradle 层面的依赖隔离，同模块内的互相引用不会被构建拦住，只能靠评审与包名约定。
  当前两个包之间零引用，合并前后保持。
- 权限点与菜单不受影响：`sys_menu` 的权限码格式（`system:user:create` 等）不变。

## D-012 为 fork 下游开扩展点（2026-10-02）

- 背景：下游项目以 git fork 跟随本仓（本仓作 upstream remote，`git merge` 同步），只新增业务模块与前台接口。
  只要下游改了任何一个上游文件，以后每次同步都可能冲突。
- 总原则：上游只开两类扩展入口——**目录约定**（`weiran4j/weiran-*/` 五层齐全即被构建自动发现）与
  **下游独占的旁路文件**（上游承诺永不创建）。下游的全部改动落在这两类位置，与上游文件不相交。
- 上游永不创建：`AGENTS.biz.md`、任何 `application-biz.yml`、`web/src/biz/`、`openspec/rules/advisory/components.biz.md`、
  `openspec/state/bizs/README.biz.md`。`weiran4j/docs/business-modules.md` 上游只保留表头与「框架 + 基座」一行，此后不再修改。
- 配套：`spring.flyway.out-of-order: true`（上下游脚本时间戳必然交错）；`@SkipApiResponse` 让 `/api/**` 之外的接口自定包络。
- 完整清单见契约 §2.2。代价：模块清单由目录扫描得出，建错目录（五层不齐）会让构建直接失败——这是有意的，静默跳过更糟。

## D-013 第三方依赖版本一分为二：框架在上游、业务在下游（2026-10-04）

- 背景：D-012 之后下游仍得改上游 `weiran-dependencies/build.gradle.kts` 才能接第三方库（首例：阿里云短信 SDK）。
- 决定：下游在独占文件 `weiran-dependencies/biz-dependencies.gradle.kts` 登记业务依赖版本与第三方 BOM，BOM 在它存在时 apply。
  宪法 CP-4 随之改写为「框架版本只在上游 BOM，业务版本只在下游清单，各自只有一处」。
- 防护：Gradle 对 `platform` 冲突取高，下游一钉版本就可能悄悄升级 Spring / Jackson。`weiran-app` 的 `check` 加 `verifyFrameworkVersions`：
  下游清单约束框架已管理的依赖一律失败；运行时类路径里框架依赖偏离框架版本也失败，除非在白名单写明理由（上游白名单在 BOM，下游白名单在下游清单）。
- 放弃：version catalog（不能 import BOM）、`enforcedPlatform`（会静默降级第三方库要的版本，同样不报错）。
- 存量：上线时上游已有两处传递漂移（snakeyaml、commons-lang3），写进上游白名单并注明来源。

## D-014 认证三段式、令牌改走 HttpOnly Cookie、外部身份的方向（2026-10-05）

- 背景：评估「支持 CAS / 联邦令牌 / 统一身份平台」时发现，认证链路揉在一个类里（`SystemTokenAuthenticator` 同时验令牌、判吊销、查权限），
  JWT 没有 `iss` / `aud`，吊销判定走 30s 进程内缓存，前端令牌存在 `localStorage`。change `auth-seams-cookie-ci`。
- 决定：
  1. **认证拆成三段**：`TokenVerifier`（按 `iss` 注册，验签名 / 有效期 / 受众）→ `IdentityResolver`（映射本地用户并判吊销）→
     `PermissionSource`（角色与权限码），由 `DispatchingTokenAuthenticator` 按令牌 `iss` 分发，不逐个校验器去试。
     框架 SPI `TokenAuthenticator` 不变。本地 JWT 写入并校验 `iss` / `aud`（默认 `weiran4j`）；配置键由 `weiran.system.jwt.*` 改为 `weiran.auth.jwt.*`（环境变量名不变）。
  2. **外部身份**（CAS / OIDC / 钉钉等）将来统一经绑定表 `sys_user_identity(provider, external_id, user_id)` 映射到本地用户，不按用户名直接对应——
     对方改名时按用户名对应会把账号串给别人。本次只定方向，不建表。
  3. **统一身份平台先买后建**：需要多系统统一身份时先用现成产品（Keycloak / 阿里云 IDaaS），本系统以联邦令牌接入方的身份对接；
     确有自研需要时，以本仓库的 fork 起一个 IAM 产品，不在本仓库里做。
  4. **Spring Security 的边界**：如果将来引入 Spring Authorization Server，Spring Security 过滤器链只匹配 `/oauth2/**`、`/.well-known/**` 与托管登录页，
     `/api/**` 仍走 `AuthInterceptor`。
  5. **浏览器令牌改走 HttpOnly Cookie**：`weiran_token`（HttpOnly）+ `weiran_csrf`（双提交 CSRF，`<userId>.<随机串>`），都是 `SameSite=Strict`；
     请求头 `X-Auth-Mode: token` 时令牌放响应体、不写 Cookie，给脚本等非浏览器调用方用 Bearer 头。前后端**写死同源部署**，不提供 CORS。
  6. **吊销判定不走缓存**：令牌版本与账号状态每次请求按主键查库；角色 / 权限快照仍缓存 30s。宪法 CP-8 随之拆为「本地令牌 / 联邦令牌」两段。
- 放弃：
  - 逐个校验器尝试（重复验签、两个签发方都认同一张令牌时有歧义）；
  - Redis 广播失效（为 30s 权限延迟引入新基础设施不划算）；
  - 响应体始终返回令牌（登录那一刻令牌仍暴露给页面脚本）；
  - 支持跨域部署（需要 `SameSite=None` + CORS 凭据，攻击面变大，且没有需求）。
- 发布影响：改名后此前签发的令牌（没有 `iss`）全部失效，需要重新登录；本地 `config/application-local.yml` 的 `weiran.system.jwt` 要改为 `weiran.auth.jwt`，
  本地 http 开发另设 `weiran.auth.cookie.secure: false`。
