# pitfalls.md —— 流水线各层踩过的坑

> **本文件没有任何机械守卫。** 唯一的唤起途径是 `CLAUDE.md` 的规则索引表。
>
> **准入门槛两条,缺一不写**:
>
> 1. **真踩过** —— 只写**在本仓库实际发生过**的失效。上游 mono4ts 的坑不要照搬:
>    技术栈不同,照搬来的条目读起来像真的,却指向一个本仓库不存在的机制,
>    比没有条目更糟 —— 它会让人去核对一件不可能发生的事,并因此信任整份清单。
> 2. **写清症状** —— 这里的坑共同点是**不报错**。只有写出「谁会因此拿到错的东西」,
>    下一个人才认得出自己正在踩它。
>
> 归属判断见 [`../README.md`](../README.md) 的决策流程 ⑤。
> 工具行为与代码库欠账(不属于流水线某一层的)写 [`toolchain.md`](toolchain.md)。

## 怎么写一条

按流水线层级归到下面对应小节,每条写三件事:

```md
### <一句话标题:失效模式,不是「XX 注意事项」>

**症状**:谁会因此拿到错的东西 / 表现成什么样(尤其:它长得像什么别的问题)。

<机制:为什么会这样,一两句>

**怎么避开**:可执行的判据或步骤。
```

## L7 硬闸门 · build / test / lint

### `git stash` 会让刚写好的 L7 证据全部失效

**症状**:三份 `exec/evidence/*.log` 刚生成完,`L7/evidence-fresh` 立刻judge它们
「比源码还旧」—— 看起来像检查器坏了,实际是自己的操作顺序问题。

`L7/evidence-fresh` 拿证据日志的时间戳与 `project.json` 里 `sourcePaths` 的最后改动时间比对,
而 `git stash push -u` 会改动 `sourcePaths` 覆盖到的那些目录的 mtime。
先写证据、后 stash 去取基线,三份日志会被一次性作废。

**怎么避开**:**怀疑有存量红灯时,先取基线,再产出证据**;没有怀疑就直接跑三条命令。
顺序反了只能重跑一遍。

## L6+L8 集成与校验

### 判为「本次不修」的问题只写在 verify.md 里 = 把它埋了

**症状**:某个越界发现被写进 `exec/verify.md` 的「遗留问题」,change 归档后
整份文件进了 `changes/archive/`,**此后没有任何入口会再翻到它** ——
问题不会消失,只是没人记得它存在过。

**怎么避开**:同时登记到 [`state/waitlist.md`](../../state/waitlist.md)
(技术用 `T-NN`,业务用 `B-NN`,同一份索引表),
并在 verify 的「遗留问题」里注明**已登记**。登记时必须带症状。

## 跨层 · 通用

### 通用 openspec-* skill 不认识本仓库的闸门

**症状**:**不报错**,流程照样走完 —— 只是 L3 的 `approved_by` / L9 的签字被静默跳过,
或者 `verify.md` 产出成一份 `check.mjs` 的 `L8/verdict-line` 认不出格式的报告。

`.claude/skills/` 下的 `openspec-*` 是 CLI 生成的通用件,不读本仓库的
`openspec/rules/` 与 `CLAUDE.md`,也不知道本仓库闸门的额外要求。

**怎么避开**:开 / 推进 / 归档 change 一律用 `devops-ff-workflow`。
完整对照见 `CLAUDE.md` 的「用哪个 skill」表。
